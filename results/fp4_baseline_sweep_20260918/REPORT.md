# 1.5×、ARCQuant 100% 质量与完整请求吞吐补测

质量与并发速度分别验收。质量使用 16 个已冻结开发场景（RBench 9、PAI-Bench 7），每场景 2 个种子；不是预留的 72 个最终场景测试。指标均为相对同输入 BF16 的一致性。

新生成：1.5×、ARCQuant 100%、SharQ 现成融合模式各 32 段视频。1.5× 的 32 个输出与冻结版本逐位一致。其他方法使用哈希核验的同条件历史输出。未重新选参，最终验证/测试集未使用。

共同条件：同版本 Edge，35 步、CFG 6、192×320、61 帧，BF16 AR 缓存并计入每请求预填充，debug off。各量化方法使用冻结的生成投影范围。我们的联合方案使用 FP4 attention；外部线性量化对照保留 BF16 attention。

本轮三个修复档保持质量实验的 `linear_backend=triton`、`kernel_variant=optimized`，使用原生 FP4 Tensor Core 计算及联合 Graph；没有在计时时另换 CUTLASS 累加实现。FP8、AWQ、ARC、SharQ 的实际原生算子由各自适配器提供，不能用配置中的默认 backend 字段推断它们的计算精度。

AWQ 行具体使用 ModelOpt 官方 `NVFP4_AWQ_LITE_CFG` 离线权重量化，保持 A16，以原始 E2M1/E4M3 codes/scales 调用 Marlin。文中的 AWQ 比较均限定为该固定实现。

## 完整请求吞吐诊断

每组计时包含输入读取、噪声生成、AR 预填充、35 步降噪、视频解码和 CPU 输出转换；不包含加载/建图、磁盘序列化和计时后的哈希检查。每档 5 轮，每轮 3 波；表中为 15 波的中位吞吐，帧/秒 = 视频/秒 × 61。

原始记录的 `additional_prepare_seconds` 单列每档新增副本的准备、建图和计时前核验；离线校准沿用冻结资产，不计入暖机请求吞吐。

当前上游 Cosmos pipeline 只支持单样本，prompt 列表会被截为首项。这里的 B 是独立完整请求的并发数，每路独立模型和 Graph，权重被复制；不是合并 GEMM 的真正大 batch，也不是共享权重服务的显存上限。

所有方法统一使用独立 Graph 捕获流，并保护 SDPA 进程级后端开关的主机调用。这两项处理请求并发兼容性，不改变选中的 attention 算法，也不增加 GPU 同步。

按用户要求，B>1 只测速度，没有输出一致性准入；隔离捕获流之前的双路预检曾出现不一致。所以并发速度不能与单请求质量合并成“同质量加速”结论。B1 路径仍核验完整质量输出。

GPU 在每波边界检查无外部计算进程；这是固定现成实现的诊断测试，performance_eligible=false，未更新正式延迟排行榜。未专项调优任何 baseline。ARC/SharQ 保留官方默认流和 eager 主机调度；其封装成本包含在计时内，不能把差距全部归因于算法 MMA。
